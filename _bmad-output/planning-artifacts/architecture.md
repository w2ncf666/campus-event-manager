# 社团活动报名与候补系统架构

以 [PRD v0.2](PRD.md) 为需求基线。采用完整方案设计，报名、候补、现场三块将并行开发，同一报名人和席位会跨模块更新。建议三位组员在这份文档上一起确认版本、数据结构和迁移负责人。

## 今天要定的三件事

| 事项 | 建议方案 |
| --- | --- |
| 开发版本 | CPython **3.14.10**、Django **5.2.19 LTS**、MySQL Community **8.4.13 LTS（InnoDB）**、mysqlclient **2.2.8**。BMAD 继续使用项目已有的 **6.12.4**。三人的开发检查和连续集成使用同一版本。 |
| 共用名单 | 一个活动、一份人员记录。报名、候补接受、现场签到与 Excel 共同引用活动内的参与者 ID。席位的正式占用和候补留位采用同一容量口径。 |
| 公共表负责人 | 建议由候补邀请负责人先整合公共模型和初始 Django migration。活动报名负责人复核报名字段和队列顺序，现场与导出负责人复核名单读取、空位交接和现场记录。M2 通过后先合入一次公共迁移，三个模块再并行接入。 |

Python、Django 和驱动已核对发布与兼容性。早期本地技术验证用的是 Python 3.10.11 和 SQLite。评审版本组合的安装及 MySQL 行锁测试安排在正式底座验证。见 [Python 发行说明](https://www.python.org/downloads/release/python-31410/)、[Django 版本支持](https://docs.djangoproject.com/en/5.2/faq/install/)、[Django 维护版本](https://www.djangoproject.com/download/)、[MySQL 发行说明](https://dev.mysql.com/doc/relnotes/mysql/8.4/en/news-8-4-13.html)和 [mysqlclient 发行文件](https://pypi.org/project/mysqlclient/2.2.8/#files)。

## 共享数据结构

以下是逻辑表和关键约束，具体迁移由公共表负责人合并两位同学的意见后生成。

| 表 | 要保存的内容 | 共用约束 |
| --- | --- | --- |
| Activity、ActivityStaff | 容量、活动时点、工作人员及其活动内岗位 | 统一以服务端时间判定，在页面显示上海时间。活动负责人、签到岗和财务按同一活动授权。 |
| Participant | 内部参与者 ID、活动 ID、学号字符串、姓名、原报名类别、当前报名状态与候补序号 | 同一活动同一学号唯一，学号保留前导零。到场核验匹配原记录。当前报名状态与操作历史分别保存。 |
| Seat | 活动 ID、逻辑席号、空位轮次、当前正式占用者 | 发布活动时按容量建立逻辑席位。每位参与者最多占一席。正式占用者退出或被释放后再次开放该席，进入新空位轮次。 |
| Invitation | 候补人、逻辑席位及轮次、原到期时点、处理结果、凭证摘要与请求 ID | 待确认且未到期的邀请占一席。一人最多一个有效留位，一席最多一个有效留位。重发沿用原席与原到期时点。 |
| VacancySkip | 逻辑席位、空位轮次、参与者、操作人和原因 | 仅过滤该空位轮次。邀请拒绝、作废或到期解除留位时，继续当前空位轮次。 |
| Attendance、RosterEvent | 签到和入场方式，以及报名轮次、释放、补录与缺席等历史 | 都引用同一参与者 ID。Excel 每人一行，原报名类别、释放和最终出席分别呈现。 |

正式名单按同一活动的当前正式占用派生。接受只能将有效留位转换成同一席的正式占用，两项更新在一个事务提交。名单服务的下一次读取立即返回新结果，当前页面用刷新触发读取，沿用 PRD 的实时口径。

## 架构决策记录

| ADR | 建议采用 | 舍弃的备选与理由 | 需求与验证 |
| --- | --- | --- | --- |
| ADR-001 应用框架 | 单体 Django，网页用 Django 模板和少量 JavaScript。共用账号会话、迁移和测试入口。 | FastAPI 可以搭同一数据库，但本组还需另行统一 ORM、迁移、会话与页面集成。Spring Boot 拥有完整的 Java 方案，现有组内环境资料尚未显示 Java 是共同熟悉的栈。 | FR-01、FR-03、FR-07、FR-11。验证三种岗位能在同一部署各自进入活动。 |
| ADR-002 数据库 | MySQL 8.4.13 InnoDB，UTF-8 和事务。CI 用对应 MySQL 验证并发。 | SQLite 适合顺序自测，但 Django 在 SQLite 上不会施加行锁。PostgreSQL 能支持事务需求，选择团队已有人熟悉的 MySQL 可以减少部署和排查成本。 | FR-02、FR-04、FR-09。用 MySQL 两个独立连接抢最后一席。 |
| ADR-003 名单与身份 | 按活动和学号核验后复用参与者 ID。报名前后的状态和历史分开保存，正式名单与导出均从共享数据读取。 | 三个模块各存一份名单再同步，邀请确认后容易出现仍读到旧名单或导出重复的人。单独按姓名合并会把同名者混为一人。 | FR-03、FR-05、FR-07、FR-09～12。检查确认名单以及现场再入场导出仍只计一人。 |
| ADR-004 名额一致性 | 名额写操作先在事务中锁定该活动，再按服务端当前时间检查状态。其中确认、释放和补位均只生效一次。 | 先查余量再无锁写入，在两次请求读到同一余量时可能多分席位。增加单独的分布式锁会带来额外服务和数据库提交协调成本。 | FR-02、FR-04、FR-05、FR-08、FR-09。AC-01 末位并发，AC-05 确认与退出重试。 |
| ADR-005 空位轮次与硬到期 | 跳过限定在席位和当次空位轮次。查询以硬到期时点判断是否仍占座，后续操作可补记到期历史并复核可用性。 | 全场跳过会让 A 丢失其他空位的原排位。单靠定时任务释放，在任务延迟时会把本应可用的席位继续显示为已占。 | FR-04～06、FR-09。AC-02 到期等号，AC-06 按空位跳过，以及 [AC-07 交接用例](https://github.com/w2ncf666/campus-event-manager/pull/3)。 |
| ADR-006 授权边界 | 工作人员由账号和活动岗位授权。参加者由本人活动会话校验，邀请另校验专属链接及确认码。 | 学号查询可以被他人代用。只有一个链接就可确认，会使错转或外泄的链接直接获得处理权。 | FR-03、FR-05、FR-11。AC-05 跨活动、错身份和错误岗位的访问。 |

## 现场负责人重点评审

用同一场限额 16 人的示例走查，初始 14 席正式占用，另两席各有一条有效邀请。

1. A 在 13:29:59 有效接受。后端提交后签到岗读取名单，立即看到 A，正式占用为 15 席，有效留位为 1 席。
2. B 没有处理邀请，13:30 起剩余留位失效并产生一个空位。14:00 前这个空位等待开场，14:00 起可按现场规则补位。
3. 原本正式但未到且无保护的 C 仍占席。14:29:59 尝试释放应失败，14:30 起由签到岗手动释放，通过同一个席位接口把空位交给现场候补。

请现场与导出负责人确认上述名单读取时点和两类空位的交接，再由公共表负责人收敛模型。架构定下后，继续拆不少于 3 个史诗和 12 个可验收故事，补项目规约与冲刺状态，经课程就绪检查和 M2 评审进入开发。
