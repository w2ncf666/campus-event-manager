## 三、真实使用者访谈提纲

建议至少联系 **1 位实际活动组织者**，尽量记录具体案例和现行做法，而不只是询问“需要什么功能”。

1. **当前流程与痛点**
   - 现在通过什么渠道发布活动、收集报名？
   - 报名名单如何管理？最麻烦、最容易出错的环节是什么？
2. **满额与候补**
   - 活动满额后，是否按照报名时间先后进入候补队列？
   - 有人退出时，是自动递补下一位，还是需要负责人审核确认？
3. **截止与取消规则**
   - 报名截止后，已报名者还能取消吗？
   - 截止后出现空位，还能从候补名单中递补吗？
4. **签到与统计**
   - 谁负责登记签到？目前通过什么方式签到？
   - 需要统计哪些数据（如报名人数、到场人数、缺席人数）？
   - 是否需要导出名单或统计结果？希望导出成什么格式？

## 四、第一版功能范围（待调研确认）

| 模块 | 初步功能设想 |
| --- | --- |
| 活动管理 | 创建和管理活动；设置活动信息、报名截止时间、人数上限（由组织者配置，不固定为 20 人） |
| 报名与候补 | 用户报名、取消报名；满额后候补；根据调研结果确定候补排序、自动/人工递补及截止后的规则 |
| 签到与统计 | 由授权负责人登记签到；查看报名和到场情况；按真实需要提供统计与导出 |

**暂不纳入第一版：** 在线支付、短信通知、学校统一身份认证等扩展功能。

> 注：上述功能仅供讨论，不代表需求已确认；具体业务规则以实际组织者反馈和课程要求为准。

## 五、选题理由与决策记录

**选题方向：** 活动报名与签到管理系统。

## 七、后续 BMAD 流程

在拿到访谈结果、明确课程要求后，再依次推进：

1. **Product Brief（`product-brief.md`）**：明确目标用户、实际痛点、项目价值与第一版范围。
2. **PRD**：逐项写清功能需求、业务规则、边界条件和验收标准，即“要做什么、什么算做对”。
3. **Architecture**：明确技术方案、系统组成与关键设计决策。
4. **Epics & Stories**：拆分为可分配、可验收的开发任务。
5. **Sprint Planning**：排定开发顺序、负责人和迭代计划。
6. **Build & Code Review**：逐项实现、测试和代码评审。
7. **Retrospective**：整理过程数据、问题和经验。

**当前优先级：先落实谁联系使用者、谁准备仓库、谁整理需求。** 在业务规则尚未确认前，不急于编写正式 PRD 或投入功能开发。
